# Метаданные сборки

StartApp 0.5 читает `compile_commands.json` и CMake File API codemodel v2/toolchains v1.
Он не запускает CMake, компилятор или команды из базы компиляции при открытии
папки. Подготовьте метаданные своего проекта привычным способом, затем
выберите каталог сборки в приложении.

## Подготовка CMake

В терминале Linux или MSYS2 UCRT64, из корня своего CMake-проекта:

```sh
mkdir -p build/.cmake/api/v1/query
touch build/.cmake/api/v1/query/codemodel-v2
touch build/.cmake/api/v1/query/toolchains-v1
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
```

В PowerShell с доступным CMake и подходящим компилятором:

```powershell
New-Item -ItemType Directory -Force 'build/.cmake/api/v1/query' | Out-Null
New-Item -ItemType File -Force 'build/.cmake/api/v1/query/codemodel-v2' | Out-Null
New-Item -ItemType File -Force 'build/.cmake/api/v1/query/toolchains-v1' | Out-Null
cmake -S . -B build -G 'Ninja Multi-Config' -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
```

Сборка бинарника для получения карты не нужна. После изменения CMake-проекта
повторите его конфигурацию, затем нажмите «Обновить карту» в StartApp.
База компиляции экспортируется генераторами Ninja/Makefiles. Генератор
Visual Studio предоставляет File API, но не `compile_commands.json`;
StartApp использует пути включений из выбранных CMake compile groups.

## Открытие и навигация

Автопоиск последовательно проверяет корень проекта, `build`, `build/windows`,
`build/linux` и использует первый каталог с базой команд или File API reply.
Для другого расположения нажмите «Каталог сборки…» или передайте путь явно:

```sh
./build/linux/startapp /путь/к/проекту --build-dir /путь/к/сборке --config Debug
./build/linux/startapp --inspect /путь/к/проекту --build-dir /путь/к/сборке --config Release > project.json
```

```powershell
& 'C:\Apps\StartApp-Windows-x64\startapp.exe' 'C:\Projects\мой проект' --build-dir 'C:\Build\мой проект' --config Debug
& 'C:\Apps\StartApp-Windows-x64\startapp-cli.exe' --inspect 'C:\Projects\мой проект' --build-dir 'C:\Build\мой проект' --config Release
```

Относительный `--build-dir` считается от корня открытого проекта. В обычном
режиме показаны включения файлов; кнопка «Цели» переключает карту на CMake.
Стрелка цели направлена к её зависимости. Выбор цели показывает тип,
число индексируемых исходников и путь артефакта. Ссылки под графом ведут к строкам
определения и зависимостей в CMake, если File API содержит их происхождение.
В списке доступны все импортированные цели, даже если текущая карта ограничена 200 узлами.

Конфигурации не объединяются: без явного выбора используется первая из File API.
Несуществующая конфигурация оставляет граф целей пустым и выдаёт замечание.
Смена каталога, конфигурации и обновление карты сохраняют буфер открытого файла.
Граф всегда отражает сохранённые файлы и последнее состояние метаданных.

## Разрешение включений

Поддерживаются `arguments` и `command`, относительный `directory`, GCC/Clang
`-I`, `-iquote`, `-isystem`, `-idirafter`, MSVC/clang-cl `/I`, `/external:I`, `/imsvc`.
Команды Windows разбираются с сохранением обратных слешей и кавычек вокруг
путей с пробелами. Предпочтительно поле `arguments`: оно не требует разбора строки.

Для `"header.h"` сначала проверяется каталог включающего файла и `-iquote`,
затем `-I`, системные пути и `-idirafter`. Для `<header.h>` первые два шага
пропускаются. Порядок внутри каждого класса сохраняется. Контекст исходника
передаётся вложенным заголовкам; циклы не обходятся бесконечно. Если общий
заголовок разрешает одно включение по-разному в двух исходниках, связь становится
неоднозначной. Для известного контекста подбор по имени файла не выполняется.
Файл за пределами индексируемой карты отмечается как «вне карты проекта».

При нескольких командах одного файла используется первая подходящая, с замечанием;
`CMAKE_INTDIR` фильтрует команды выбранной конфигурации. При нескольких
конфигурациях File API команда без такого признака не заменяет выбранную группу.
Несколько CMake-групп одного исходника также не объединяются.

Полноценный препроцессор пока не реализован: `#if`, макросы, встроенные пути
компилятора, `INCLUDE` из окружения, response-файлы `@file`, sysroot-пути `=...`,
старый `-I-`, PCH, header maps и особенности поиска MSVC по стеку включений
не моделируются. Это карта для навигации; точная диагностика компилятора
и clangd относятся к следующему этапу.

## JSON и ограничения

Вкладка «Сборка» показывает найденные инструменты отдельно от настроенного
генератора. Имя генератора, его multi-config режим и версия CMake берутся из
индекса File API; `toolchains-v1` даёт язык, идентификатор, версию и путь компилятора.
Без reply читается `CMakeCache.txt` (генератор, конфигурации, пути C/C++ компиляторов).
Без сведений о toolchain база компиляции даёт только имя команды; её версия
не угадывается. Для выбранной цели показан артефакт именно текущей конфигурации.

`CMakePresets.json` и `CMakeUserPresets.json` читаются даже без каталога сборки.
Импортируются configure/build-пресеты, наследование, configurePreset,
генератор, binaryDir и конфигурация. Локальные JSON include внутри проекта
обходятся с ограничением 32 файла/8 уровней; наследование защищено от циклов.
Скрытые пресеты используются для наследования и остаются в JSON, но не занимают
панель. Значения binaryDir отображаются как объявлены, без раскрытия макросов.
Условия, переменные окружения, toolchainFile, workflow/test/package-пресеты
и макросы include пока не интерпретируются: наличие объявления не подтверждает
его применимость на текущей ОС. Пресет не выбирается и не запускается автоматически.

`--inspect` сохраняет `files`, `includes`, `targets`, `target_dependencies`,
`build_directory`, `configuration`, `configurations` и `notes`.
Объект `build_profile` содержит версию CMake, генератор, multi_config,
массивы `compilers` и `presets` с источниками данных.
У файлов есть пути поиска и `settings_source`; у включений — признаки
`metadata`, `ambiguous`, `outside_project` и источник настроек. Цели содержат
идентификатор CMake, имя, тип, артефакт, исходники и место определения.
Связи целей используют идентификаторы, а не имена. Неизвестные значения — `null`.
Сырые команды и значения `-D` в экспорт не попадают.

Один JSON-файл ограничен 16 MiB; импорт — 20 000 командами и 2 000 целями.
Используется последний индекс File API по имени. Ссылки reply принимаются только
как имена JSON-файлов в том же каталоге; `../` и символические ссылки на файлы
не принимаются. Некорректные данные приводят к замечаниям, сохраняя доступ к исходникам.
Старые метаданные не обновляются автоматически: актуальность зависит от
последнего запуска конфигурации пользователем.
